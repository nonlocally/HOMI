The one idea

Everything here follows from a single correction to how agents talk to each other.

Before homi, agent messaging was rendezvous: both ends had to be alive at the same instant, and a "name" was whatever a live process's sidecar file happened to say right now. Miss the window — the agent finished its turn, the laptop slept, the session restarted — and the message was simply gone. The name pointed at a corpse.

homi replaces rendezvous with store-and-forward. A name is claimed and becomes a durable address that outlives the process behind it: an always-answerable socket, an entry that stays in the roster, and a mailbox on disk that captures every inbound message before anything else is attempted. When a real session takes the name, held mail drains into it as conversation turns. When the session dies, homi takes the name back and keeps holding. The gap between received and acted on stops being your problem — it becomes the daemon's.

Why it matters. Once an address survives its process, every hard thing becomes possible: talking to an agent that's asleep, waking it with a message, moving it to another machine without losing its inbox, containing it in a VM, and handing a capability to a collaborator — all without a central server, because the durability lives next to each agent, not in a cloud.

Four invariants

These are the rules the whole system is held to. Every feature honors all four, and the test suite exists to keep them honored.

01

Identity ≠ process lifetime

A claimed name is a stable socket + sweep-proof roster entry + durable mailbox. The session behind it can come and go; the address doesn't move.

02

Never advertise the unmeasured

Liveness is probed (connect + recv), never inferred from a file existing — and every route is labelled probed / reported / boxed-probed. A daemon even probes its own published address.

03

Durability before delivery

A message is fsync'd to the mailbox before it is acked or delivered. Cursors only move forward. Cross-device is at-least-once, deduped by msg_id.

04

Decouple failure domains

Inbound and outbound fail independently; each device links outbound-only. One machine sleeping never wedges another. Trust boundaries deny by default.

Two planes

homi separates two fundamentally different ways to reach an agent, and never confuses them.

Messages — the default

Identity-addressed, durable, acked. You send to a name; delivery is store-and-forward, so the target need not be alive. This is how agents should talk to each other — it survives sleep, restarts, and device boundaries.

sendaskgroupnotifyinbox

Seats — the escape hatch

Keystroke-level, observed, ephemeral surfaces you cannot mailbox: a cluster login shell, a REPL, a TUI. Explicit, opt-in per link, and fail-closed. You drive them; you don't converse with them.

spawnsendreadstatewaitrespond
The discipline that killed the old system's "swarm" layer: it drove agents by blindly typing into tmux panes (a message plane built out of seats). homi's message plane is durable and acked; seats are the narrow, explicit exception — never the default.

When a real session adopts the name (via /rename, which the sidecar mirrors), homi steps aside and drains held mail into it. When the session vanishes, homi re-plants its own sweep-proof entry and resumes holding. Nothing is lost in the handoff either direction.

Message plane

The durable core. Beyond fire-and-forget send, the fabric adds the pieces a real conversation needs.

ask — a blocking, correlated question

ask sends a question carrying a return token (asker@device~corr) and blocks until the correlated reply lands — whether the answer comes back via an explicit reply <token> or, best-effort, as a plain message back to the asker. It works across device and fleet boundaries, where the token is rewritten so replies route home.

communicate homi ask helper "say hi in one word" --from you --timeout 120
# blocks, then prints the correlated reply — proven live at 10.09s round-trip

group & notify

group fans one message to a set of names. notify is the durable human-summon lane — it writes a reason record and can fire a hook (HOMI_NOTIFY_CMD) — for when an agent is blocked on a decision only you can make. wait long-polls a mailbox for the next new message (the inbound wake for runtimes with no socket push).

Seats — driving surfaces you can't mailbox

Some things have no mailbox: an HPC login node behind Duo, a Python REPL, a TUI. A seat is a driven tmux surface, rebuilt clean-room from hard-won discipline (not inherited code):

  • A state classifier — dead > approval > busy > booting > idle, read from the signals that survive answer-streaming (title-spinner animation with jittered sampling; the "esc to interrupt" hint; the idle footer).
  • Deliver-and-verify send — sanitize, stage the text literally, submit with a separate, retried Enter, and verify the composer actually cleared; returns an explicit "unconfirmed" rather than lying. It never re-sends text (which could duplicate a prompt).
  • Fail-closed respond — answering an approval dialog parses only the real menu block (never the surrounding prose), drives the highlight to a matching option, verifies it landed, and refuses if nothing clearly matches. A bare Enter on an unknown default is never pressed.
  • Secret-redacting read — tokens are masked on screen-read unless you pass --raw.

Seats work across devices too: seat spawn --device air-2 returns air-2:%N, and every seat verb accepts that form. Cross-device seat control is opt-in per link (--allow-seats, upgradable and revocable in place) and carried by synchronous envelopes whose ack returns the result.

This is the proof case for the cluster conductor: a host agent drives a human-authenticated SSH login pane, greps the job's self-reported coordinates out of the log, and gates the irreversible sbatch behind a durable human reply — no cluster-side daemon, works on any Slurm login node you can reach.

Spawn — the fabric creates agents

One verb stands up a whole agent: spawn = claim a durable identity + launch the CLI in a seat + bind the two + adopt (drive /rename so the live session carries the fabric name). The result is one being that is both reachable by mail and watchable in a seat.

communicate homi spawn scout --cli claude --cwd ~/src/aadarwal/communicate
# claim + seat + bind + adopted:true — then it answers `ask` on its own

Workers launch with crossSessionInbound: accept scoped to their own process, so a mailbox-driven agent receives mail as turns without a human clicking through a gate every time — a worker that needs a click per message is broken by construction. fan makes N of them plus an addressable group; consult spawns-or- reuses a private peer and asks it one question.

Move an agent between machines

The address stays alive the whole way across.

An agent-being is three JSON artifacts: its transcript (its mind), its mailbox (inbox + cursor), and its identity claim. move relocates all three. The old beam tool moved only the transcript and let the address die at the origin — mail kept landing in a dead inbox. homi fixes exactly that: the move order is chosen so the name never points at nothing.

originholds the claim
depart→
proxy → targetaddress alive
link→
targetclaims + merges
the instant depart runs, mail to the name routes over the link to the new home
1
premove — verify the agent is local here; refuse a live session unless you explicitly --fork --as <new>. Report the mailbox truthfully.
2
transcript rsync — copy the mind while the origin still owns the name (safe; nothing has changed hands).
3
depart — atomically release the claim and re-bind the name as a proxy homed at the target. From this instant, new mail routes over the link; the target auto-claims on first delivery. the address never dies
4
mailbox rsync — the inbox is now frozen at the origin; stage it on the target.
5
arrive — claim + a recomposing merge: delivered history stays behind the cursor (a resumed session never re-receives mail it already acted on); every undelivered line — including stragglers that raced in mid-move — waits after it. Idempotent by msg_id.
6
--spawn (optional) — resume the transcript in a seat on the target via the cross-device seat plane.

Proven live mini-2 → air-2: after the move, a bare-name send at the origin landed in the far inbox, and the transcript was resumable there with claude --resume <sid>.

Boxed agents — a VM as a first-class peer

A sandboxed agent should still be a real member of the fabric. The problem is direction: the measurements (against Apple's container) showed that a host cannot reach into a VM by IP (per-process TCC blocks it) or through a mounted socket (inert over virtiofs) — but a container can publish a socket out to the host over vsock. So the rule is inverted: the box publishes; the host adopts. A box is a device one vsock-hop away.

verified live: the air gap held (ENETUNREACH to 1.1.1.1) while mail flowed both ways

claim --boxed records the container-published socket as the identity's address (homi never binds it), probes it for measured liveness (boxed-probed), delivers mail through it, and drains the box's outbox with the boxed identity as attribution. The maximally hardened posture — --network none, where the box's only egress is its own mailbox — is the configuration proven working end to end, not a compromise.

Fleets — capability, not credentials

Two people, two machines, two tailnets. The goal is for a collaborator to reach one of your agents — not to hand them an account. A cross-fleet link is deny-by-default and passes through six independent layers; a foreign message must satisfy all of them, and compromising one buys only the floor of the next.

L0
Network — a tailnet ACL row, one host, one port
revoke: unshare
L1
Transport — a forward-only key: restrict,port-forwarding,command="/usr/bin/false". No shell, no exec, no PTY — only a socket forward.
revoke: delete the key line
L2
Link — arrival-line attribution: whatever lands on in/<fleet>.sock is that fleet; deduped, acked
revoke: federate unlink
L3
Identity — grant<fleet><name> exposes one agent; ungranted or unclaimed → one ambiguous error (no enumeration, no auto-claim oracle)
revoke: ungrant
L4
Delivery — mailbox-first durability; a bypass-mode session still holds a foreign turn for your approval
revoke: don't approve
L5
Execution — the payload is only text; it gains power solely through the receiving agent's own sandbox
revoke: agent's config

Onboarding is a pair of base64 cards exchanged over a trusted channel (federate invite / accept). A card carries the fleet name, address, tailscale IP, an ed25519 fleet-key fingerprint, and the inbound socket path — the path is carried because the forward-only key cannot run echo $HOME to discover it. Foreign senders appear locally as fleet-qualified proxies (orchestrator@alice), so a foreign fleet can never shadow a local name.

The pattern in practice — a librarian, not an account. To share cluster access, you don't create a login for your collaborator; you publish an agent whose capability is the cluster and grant them mail to it. It runs as you, with your credentials (which never cross the boundary), and gates every node-hour spend behind your own approval. The capability crosses; the account does not.

Security model

What's actually enforced — measured and tested, not aspirational:

BoundaryGuard
Fleet maildeny-by-default grants · one ambiguous error (no name enumeration) · no auto-claim oracle · fleet-qualified proxies

The self-review

Before calling any of this done, an adversarial reviewer went over the whole ~4,800-line diff. The core message plane came back clean — lock ordering sound, no deadlocks. The real failure modes clustered exactly where the new trust boundaries were. Every finding is fixed, and each fix is pinned by a regression test that fails if the guard comes undone.

critical · fixed

Fleet status oracle

A fleet peer could call status unauthenticated and receive your whole roster — defeating the very name-masking the fleet path implements. Now token-gated like every other op.

critical · fixed

authorized_keys injection

A crafted card could smuggle a newline and write a second, unrestricted key = host compromise. Card fields are now strictly validated; malformed cards are refused before anything is written.

Also fixed: boxed re-offer dedup (double-delivery after a lost ack), a boxed drain thread leak on release, an arrive/deliver cursor race, respond --deny auto-approving on a highlighted "Yes", a move --as rsync injection, and a concurrent-autostart split-brain. Two low-risk minors (a per-fleet proxy cap; a sub-millisecond depart window) are noted as follow-ups rather than guessed at.

Every route carries its provenance — how the fabric knows what it's telling you. This is invariant #2 made visible:

What your agent is told

This is the part that decides whether any of it gets used well. An agent doesn't read this site — it reads three things.

1 · The orientation it receives on connect

The moment an MCP client connects, the homi server hands the model an instructions string. Without it, an agent sees 26 tool names and no theory of the system. This is the exact text, verbatim:

homi gives you a DURABLE IDENTITY and a MAILBOX that outlive your process.

Start with whoami (who am I here?) and agents_list (who else exists, with MEASURED
liveness). If you have held mail, inbox_read shows it.

TWO PLANES — pick the right one:
• MESSAGES are the default for agent-to-agent. send/ask reach an agent BY NAME even
  if it is not running: mail is stored durably and delivered as a turn when it wakes.
  Never poll for an agent to come up — just send. Use ask when you need the answer
  (it blocks for a correlated reply); use send to fire and forget; group_send for many.
  Address another device as name@device.
• SEATS are the ESCAPE HATCH for surfaces you CANNOT mailbox — a cluster login shell,
  a REPL, a TUI. seat_state is the non-blocking done-check (one word); never scrape
  seat_read to find out whether something finished. seat_wait blocks until idle.
  seat_respond is fail-closed: it refuses rather than guess at an approval prompt.
  Do NOT drive another agent through a seat — that is what send/ask are for.

CREATING AGENTS: spawn claims an identity, launches the CLI in a seat, binds them, and
adopts the name — the result is reachable by mail AND watchable. fan spawns a team,
consult asks another model one question. move relocates an agent (transcript + mailbox
+ identity) to another device with its address alive the whole way.

WHEN YOU ARE BLOCKED on a decision only the human can make, call notify with a real
reason — do not stall silently.

Not exposed here on purpose: federation, grants, and linking are human trust decisions
made on the CLI, never by an agent.
Why it's written like that. Every line answers a mistake agents actually make: polling for a peer to come up (instead of just sending), scraping a screen to find out if something finished (instead of asking for the state), driving another agent by typing at it (instead of messaging it), and stalling silently when blocked. The register matters more than the prose — it teaches when, not just what.

3 · What an inbound message looks like to the agent

Mail doesn't arrive as an API response — it arrives as a conversation turn, wrapped so the model can see who it's from and can't be spoofed by the body text:

<cross-session-message from="uds:/tmp/cc-socks/homi-orchestrator.sock"
                       from-name="orchestrator">
look at the failing test in ./api

[reply with: communicate homi reply orchestrator@mini-2~a3f9…c1 "<answer>" --from scout]
</cross-session-message>

If the message came from an ask, it carries a return token. The agent answers by running that command (or calling the reply tool) — and the asker's blocked call, possibly on another machine, resolves with the answer. That round trip is what was proven live at 10.09 seconds.

No cloud, no broker, no polling loop. Here is the actual path, on your own hardware.

homi plants its own sweep-proof sidecar for every claimed name, so the name stays listed even when nothing is running behind it — then steps aside when a real session adopts that name. That handoff, in both directions, is why an address never disappears.

Across your devices

device Aout/<dev>/ queue
ssh -N -L→
device Bin/<A>.sock

each device dials OUTBOUND only · the ack comes after durable storage, never before

Each side opens its own outbound SSH tunnel to the other's per-peer inbound socket. That's invariant #4: your inbound and outbound fail independently, so one machine sleeping can never wedge the other. Messages queue under out/<device>/, retry with exponential backoff, dedupe by msg_id, and dead-letter if the far side gives a deterministic refusal. Attribution comes from the arrival line — whatever lands on in/air-2.sock is from air-2, regardless of what the message claims about itself.

The plugin story — where this stands

Being usable by an agent has three layers. homi has the first, and the third is the honest gap:

shipped

The distinction matters and is easy to miss: claude mcp add can deliver tools, and it can deliver the instructions string — but it can never deliver a hook or a skill. Those are plugin artifacts. Until homi ships as a plugin, an agent only learns it has a mailbox when it happens to call a tool; with a SessionStart hook, it knows before its first move — and Codex gets the same text through the same contract.

Why it isn't built yet. Deliberate sequencing. A plugin is the packaging of a settled thing; the fabric is settled now, so this is the natural next build — not something to have rushed alongside it.

Operating it

Everyday

communicate homi status              # sockets, identities, links, queues
communicate homi agents              # just the roster
communicate homi inbox <name>        # read any mailbox
communicate homi install / uninstall # launchd / systemd persistence

When something looks wrong

SymptomWhat it means / what to do
An agent reads stored, not liveNothing is running behind that name. This is fine — mail is being held. It'll drain when the agent comes up.
A far device is unreachableProbably asleep. Its queue keeps filling and drains on wake; nothing needs restarting. Check link_status for depth and last error.
Messages land in out/<dev>/dead/The far side gave a deterministic refusal (bad name, ungranted). Retrying wouldn't help — that's why it's dead-lettered rather than looping.
A seat won't take inputseat_state first. If approval, something is waiting on a prompt; seat_read to see it.
Control ops refusedYou have a fleet link, so the control socket needs the token — the CLI attaches it automatically, so this means you're reaching it from somewhere unusual.

Turning it off

communicate down deliberately does not stop homi — the fabric is infrastructure, not a session. Use homi stop for now, or homi uninstall to remove persistence. Neither touches a single mailbox.
